# H런처 동작 원리 — 외부 메모리 읽기

H런처가 대기방/인게임 참가자와 배틀태그를 어떻게 가져오는지 설명하는 문서다.
결론부터: **화면 캡처(스크린샷)도, 게임 주입(인젝션)도 아닌 "외부 프로세스 메모리
읽기(External Memory Reading)"** 방식이다.

---

## 1. 세 가지 접근 비교

| 방식 | 무엇을 하나 | H런처 |
|------|-------------|-------|
| 스크린샷 + OCR | 화면을 이미지로 찍어 글자를 인식 | ❌ 안 씀 |
| 인젝션(DLL 주입) | 게임 **안에** 코드를 넣어 내부에서 읽음 | ❌ 안 씀 |
| **외부 메모리 읽기** | 게임이 RAM에 올려둔 데이터를 **밖에서 복사해** 읽음 | ✅ **이 방식** |

핵심 이점:
- **스크린샷 대비** — 화면에 안 보이는 값(배틀태그는 화면에 안 뜸)도 읽고, 정확하다.
- **인젝션 대비** — 게임 프로세스를 건드리지 않아 밴/크래시 위험이 훨씬 낮다.
  (인젝션은 안티치트가 핵으로 오인할 수 있다.)

> 왜 이게 가능한가? 게임은 서버에서 받은 (암호화된) 데이터를 **자기가 쓰려고
> RAM에 복호화해서 풀어놓는다.** 우리는 그 **이미 복호화된 데이터**를 옆에서 읽을
> 뿐이다. 그래서 네트워크 패킷을 직접 해독할 필요가 없다.

---

## 2. 읽는 파이프라인

Windows API 4개로 이뤄진다 (`internal/memscan`).

```
OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION, pid)
        │  StarCraft 프로세스를 "읽기 권한"으로 연다
        ▼
VirtualQueryEx(주소)  ── 반복 ──▶  메모리 영역 목록
        │  각 영역의 상태/타입/크기/보호속성을 조회
        │  필터: MEM_COMMIT + MEM_PRIVATE(힙) + ≤96MB + 읽기가능 + 비가드
        ▼
ReadProcessMemory(base, size)
        │  선택한 영역을 1MB 청크 단위로 우리 프로세스로 복사
        ▼
바이트 패턴 검색·파싱 (bytes.Index / 수동 스캔)
        │  JSON 문자열과 바이너리 구조체를 찾아 해석
        ▼
닉네임 → 배틀태그 저장 (identities.json)
```

영역 필터가 중요하다. 게임 RAM은 수 GB라 전부 읽으면 느리다. **개인 힙(MEM_PRIVATE)
+ 96MB 이하** 영역만 고르면 참가자/배틀태그 데이터(전부 작은 PRIVATE 영역에 있음)는
놓치지 않으면서 텍스처·오디오 같은 큰 버퍼는 건너뛴다.

---

## 3. 읽어내는 데이터 구조

StarCraft: Remastered는 대기방/채널 상태를 **JSON 이벤트**로, 인게임은 **브루드워
엔진 구조체**로 메모리에 들고 있다.

### (a) 대기방 슬롯 — `SetPlayerData` JSON

방에 있는 각 슬롯을 서술한다. 닉네임·종족·핑은 있지만 **배틀태그는 없다.**

```json
"endpoint":"SetPlayerData","data":{
  "id":3,"name":"mu1iham","race":"Terran","color":"...",
  "state":"human","latency":0,"latencyBars":5
}
```

### (b) 배틀태그 — 두 가지 소스

배틀태그는 닉네임과 따로 떨어져 있어서, 이걸 **연결(name → battleTag)**하는 게 핵심이다.

**소스 1: 채널/입장 이벤트 JSON** (`OnChannelMemberJoined`, `OnMessage`)

```json
"OnChannelMemberJoined","data":{"channelMember":{
  "id":164,"name":"ipark805","battleTag":"now4aa#3133",
  "prettyBattleTag":"now4aa","legacyChatToonId":695, ...
}}
```

`"battleTag":"` 를 찾아 근처의 `name` 필드와 짝지어 저장한다.

**소스 2: 바이너리 프로필 구조체** (JSON이 잘려도 잡히는 백업 소스)

일부 유저는 프로필이 이진 구조체로 남는다. **배틀태그 문자열 시작점에서 정확히
+0xC8(200바이트) 뒤가 닉네임**이다.

```
[헤더][battleTag "condaactivat#3668"\0][ ~180B ][nickname "mu1iham"\0]
       └──────────────── +0xC8 ────────────────┘
```

`#` 뒤에 숫자가 오고 NUL로 끝나는 배틀태그를 찾은 뒤, +0xC8 위치에 유효한 닉네임이
있으면 짝지어 저장한다. 이 소스 덕분에 커버리지가 크게 올라간다.

### (c) 인게임 플레이어 배열 — 브루드워 구조체

게임이 시작되면 위 JSON 이벤트들은 메모리에서 **파괴된다.** 하지만 스타는 내부적으로
브루드워 엔진이라 **36바이트짜리 플레이어 구조체 배열**을 유지한다.

```
struct Player (36바이트 = 0x24):
  +0x00  u32  playerID        (슬롯 번호 0~11)
  +0x04  u32  stormId         (빈 슬롯은 0xFFFFFFFF)
  +0x08  u8   type            (2 = 사람)
  +0x09  u8   race            (0젅 1테 2톀 6랜)
  +0x0A  u8   team
  +0x0B  char name[25]        NUL 패딩
```

이 배열을 **시그니처 스캔**으로 찾는다(작은 정수 + 출력가능 이름 패턴). 주소가
매번 바뀌어도(ASLR) 패턴으로 찾으므로 인젝션이 필요 없다. 배틀태그는 배열에 없으니
닉네임으로 저장소에서 조회해 붙인다.

### (d) 내 슬롯 — `SetLocalPlayer`

```json
"SetLocalPlayer","data":{"id":3, ...}
```

`id`가 **내 슬롯 번호**다. 이걸로 "나"를 식별해 최근 목록에서 제외하고, 참가자
목록에 "나" 표시를 한다.

---

## 4. 상태 판별과 페이싱

한 번의 스캔으로 현재 화면 상태를 구분한다.

- **대기방(Lobby)** — 사람이 든 `SetPlayerData`가 있음 → 실시간 표시(핑 포함)
- **채널(Channel)** — 로비는 없지만 배틀태그 이벤트가 많음 → 배틀태그 수집만
- **인게임(InGame)** — 로비 없음 + 플레이어 배열 존재 → 배열에서 명단 표시
- **대기/메뉴(Idle)** — 아무 데이터 없음 → 목록 비움

상태별로 스캔 주기를 바꿔 게임 렉을 막는다(로비 3초 / 채널 6초 / 인게임 20초).
새로고침 버튼은 이 주기를 무시하고 즉시 재스캔한다.

**성능 최적화:** 슬롯 읽기와 배틀태그 수집을 **한 번의 메모리 패스**로 합쳐서
매 스캔의 메모리 복사량을 절반으로 줄였다.

---

## 5. 한계 (정직하게)

- **인게임 실시간 값 중 핑은 없다.** 플레이어 배열엔 지연시간이 없다.
- **배틀태그는 100% 커버 불가.** 완전 유휴 유저(오래전 채널 입장, 프로필 미로드,
  이벤트 만료)는 배틀태그가 메모리 어디에도 없다. 실시간 주입 후킹만이 100%를
  달성하지만, 밴 위험 때문에 쓰지 않는다. 대신 **여러 판에 걸쳐 누적**한다.
- **드랍 공격의 "범인"은 특정 불가.** 네트워크 레벨 공격이라 메모리에 원본이 없다.
  누가 빠졌는지(피해자)만 알 수 있다.

## 6. 관련 소스

| 파일 | 역할 |
|------|------|
| `internal/memscan` | OpenProcess/VirtualQueryEx/ReadProcessMemory 래퍼, 영역 필터 |
| `internal/roster` | SetPlayerData·배틀태그·프로필구조체·인게임배열 파싱 |
| `internal/identity` | 닉네임→배틀태그 영속 저장 |
| `internal/blacklist` | 블랙/화이트 리스트 (battleTag 키) |
| `internal/recents` | 최근 함께 플레이한 유저 기록 |
| `internal/app` | 상태 판별·페이싱·드랍감지·자기식별 오케스트레이션 |
| `internal/ui` | WebView2 창 + HTML/CSS/JS |
| `cmd/hlmem` | 진단 도구(search/dump/regions/players/events/roster/ingame/cluster/locate) |
